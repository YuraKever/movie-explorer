# 🤖 Movie Explorer — план RAG: семантический поиск и AI-советник

**Цель:** пользователь пишет «что-то атмосферное про одиночество в космосе, не слишком
длинное» и получает карточки фильмов из нашей базы, у каждой одна строка «почему подходит».

**RAG (Retrieval-Augmented Generation):** перед вызовом LLM мы **находим** в своих данных
релевантные документы и **подкладываем** их в промпт. Модель отвечает по нашим данным, а не
по памяти.

```
ИНДЕКСАЦИЯ (офлайн, один раз / по крону)
  TMDB → текст документа → embedMany() → векторы → Postgres (pgvector)

ЗАПРОС (на каждый вопрос)
  вопрос → embed() → поиск ближайших векторов → top-K фильмов
        → промпт «выбирай только из этих фильмов» → LLM → { picks: [{ movieId, reason }] }
```

**Порядок:** сначала **R** (поиск), потом **G** (генерация). Поиск можно увидеть и проверить
руками без LLM. Если он плохой, никакая модель ответ не спасёт. Методология та же, что в
[PLAN.md](PLAN.md): tracer bullet, каждый шаг — рабочий вертикальный срез.

## Шаг 3 — Схема

Новый файл `src/lib/db/movie-embeddings-schema.ts`, экспорт в `schema.ts` (как favorites):

```
movie_embeddings
  movie_id      integer PK        — TMDB id
  content       text              — ровно тот текст, который эмбеддили
  content_hash  text              — чтобы не переэмбеддить неизменившееся
  embedding     vector(1024)
  updated_at    timestamp
  + HNSW-индекс по embedding (vector_cosine_ops)
```

- [x] Схема + `npm run db:generate` + `npm run db:migrate`

**Что понять:**
- **Зачем хранить `content`:** для отладки («почему он нашёл это?») и чтобы положить его в
  промпт на шаге G без лишнего запроса в TMDB.
- **HNSW** — индекс для *приблизительного* поиска ближайших соседей. Без него Postgres
  сравнивает запрос со всеми строками. На 5 тыс. строк и это быстро, но индекс — правильная
  привычка и вопрос на собеседовании: «exact vs approximate nearest neighbours».
- **Cosine:** важен угол между векторами, а не длина. Стандарт для текстовых эмбеддингов.

**Проверка руками:** `select movie_id, left(content, 80) from movie_embeddings limit 5;`
и `select count(*) from movie_embeddings;`

**Что понять:**
- **Качество RAG на 80% определяется тем, что ты эмбеддишь.** Если в тексте есть только
  название, ищется только по названию. Keywords из TMDB сильно улучшают поиск.
- **Chunking здесь не нужен:** один фильм = один короткий документ. Длинные тексты (статьи,
  PDF) режут на куски по ~500–1000 токенов с перекрытием, и один источник даёт много векторов.
  Важно понимать, что мы сознательно этого не делаем и почему.
- **Индексация — офлайн-процесс**, не часть запроса пользователя. В проде она идёт по крону или
  при появлении новых данных.
- **Техническое:** скрипт запускается через `tsx` (явная devDependency): он понимает TypeScript
  и алиас `@/`; `--env-file-if-exists=.env.local` подгружает env **до** импортов (пул БД
  создаётся при импорте `@/lib/db`).
- **Результат первого прогона:** 883 фильма за ~84 с; повторный прогон — 0 к эмбеддингу.

## Шаг 5 — Retrieval

`src/features/ai/retrieve.server.ts` (стиль `*.server.ts`, как в `features/movies`):

```
findSimilarMovies(query, { k = 8 }) →
  1. embed(query) ТОЙ ЖЕ моделью, что при индексации
  2. SELECT … ORDER BY embedding <=> $queryVector LIMIT k
  3. [{ movieId, content, distance }]
```

- [x] Функция поиска
- [x] Порог по `distance`: если даже лучший результат далеко, вернуть «ничего не нашёл»

- [x] Инструкция к запросу (`embeddingQuery` в `ai.ts`): Qwen3-Embedding асимметричная.
      Начало 8 → 1 место, Матрица 3 → 1, Заклятие 3 → 1; Интерстеллар 1 → 3 (в топе остался)
- [x] `MAX_DISTANCE = 0.55`: релевантное ≤ 0.54, «asdf qwerty» 0.59, «рецепт борща» 0.67

**Проверено в шаге 9:** фильтр `*creditsstinger` оставлен (метрики не хуже, WALL·E ближе);
фильтр всех служебных тегов откатан (MRR хуже).

**Что понять:**
- Запрос и документы эмбеддятся **одной моделью**. Это самая частая ошибка.
- `ORDER BY distance` по возрастанию: только в такой форме используется HNSW-индекс.
  Сортировка по `1 − distance` DESC выглядит так же, но индекс не задействует.

**Известные ограничения 4B-модели (→ evals, шаг 9):** иногда объяснение на английском

- **Structured output, а не текст:** результат — это данные (id), а не абзац. Его можно

- **Пока без стриминга:** ответ короткий, а structured output со стримингом сложнее. Стриминг

- **Prompt injection:** пользователь может написать «игнорируй инструкции». У модели нет tools,
  она видит только список фильмов и ничего не может «сделать», поэтому риск минимален. Стоит
  понимать, *почему* он минимален.
- Точные API AI SDK 7 (`generateText` + схема вывода, мок-модели) сверять с
  `node_modules/ai/docs`, по памяти не писать.

**Результаты (один и тот же индекс, 912 фильмов):**

| Что | recall@8 | MRR | Итог |
|---|---|---|---|
| База | 87.5% | 0.763 | WALL·E #5 (0.483) |
| A: убрать `*creditsstinger` | 87.5% | 0.763 | WALL·E #5 (**0.475**) — **оставлено** |
| B: + sequel, prequel, remake, reboot, spin off, woman director | 87.5% | 0.754 | Insidious 3→4, Hachi 2→3, Parasite 7→8 — **откатано** |

| Порог | Отрезает ожидаемых (из 20 в top-8) | Пропускает бессмыслиц (из 4) |
|---|---|---|
| 0.50 | 5 | 0 |
| **0.55** | **1** (Weathering with You, 0.563, «уютный вечер») | **0** |
| 0.60 | 0 | 1 («asdf qwerty», 0.591) |

→ **0.55 остаётся**: единственная потеря — запрос про настроение, а 0.6 уже пропускает мусор.

**Советник (`--advisor`, 11 русских запросов):** объяснения на русском 16/17 (94%),
ожидаемые фильмы в ответе 10/14. Поиск нашёл Интерстеллар (#3) и Хатико (#2), но модель
их **не выбрала** — узкое место теперь генерация, а не поиск.

**Провалы поиска (не в top-8):** «Keanu Reeves» → Матрица не в top-40 (актёров нет в
документах); «уютное на вечер под дождь» → Amélie не в top-40; «feel-good… happy tears» →
1+1 #11, Up и Coco не в top-40. Все три — «трудные» запросы: имена и чистое настроение.

**Что понять:**
- **recall@8** отвечает «нашли ли вообще» — в top-8 попадают кандидаты для модели, дальше
  она не видит. **MRR** — «насколько высоко»: чувствует, что Parasite сполз с 7 на 8, хотя
  recall этого не заметил. Одна метрика прячет то, что видит другая.
- **Меряй на одинаковых данных.** Первый замер фильтра дал MRR 0.765 → 0.763, как будто
  хуже. Но между прогонами TMDB обновил списки (885 → 882 фильма). На том же наборе база
  тоже 0.763 — «ухудшение» было дрейфом данных, а не эффектом изменения.
- **Интуиция ошибается:** «убрать все служебные теги» звучит правильно, но сиквелы без тега
  `sequel` стали ближе к запросам про оригиналы. Без eval это бы прошло незамеченным.
- **Отрицательные примеры обязательны.** Без бессмыслиц порог 0.65 выглядел бы лучше всех
  (0 потерь) — пропуск мусора видно только на запросах, где правильный ответ «ничего».

      индексация берёт `append_to_response=keywords,credits`; полная переиндексация ~100 с
- [x] **B — гибридный поиск:** GIN-индекс по `to_tsvector('english', content)` (индекс по

      `fuseRankings` в `hybrid.ts`
- [x] Порог: совпадение по тексту проходит всегда, найденное только по смыслу — если ≤ 0.55
      (`passesThreshold`); 4 бессмыслицы по-прежнему не проходят
- [x] Детерминизм: текстовые совпадения при равном `ts_rank` сортируются по расстоянию

**Результаты (один и тот же набор вопросов; A и A+B — на одном индексе):**

| Вариант | plot recall@8 / MRR | names recall@8 / MRR | бессмыслиц прошло |
|---|---|---|---|
| База (только вектор) | 92.1% / 0.804 | 40.5% / 0.516 | 0 / 4 |
| B — гибрид без имён в документе | 92.1% / 0.804 | 40.5% / 0.516 | 0 / 4 |
| A — имена в документе, только вектор | 92.1% / 0.794 | 71.4% / 0.762 | 0 / 4 |

| **A + B (итог)** | **92.1% / 0.794** | **76.2% / 0.800** | **0 / 4** |

**Советник (`--advisor`, 12 русских вопросов):** объяснения на русском 15/18 (83%), ожидаемых
фильмов в ответе 11/17. Было (шаг 9, 11 вопросов): 16/17 и 10/14 — язык просел, вероятно
из-за английских имён в контексте кандидатов.

**Не делаем (и почему):** reranking — у Ollama нет rerank-эндпоинта; стриминг — ответ
структурированный и короткий; фильтры по метаданным — отдельная UI-задача, к качеству
поиска по смыслу не относится.

**Что понять:**
- **B без A ничего не дал** — полнотекстовому поиску нечего искать, если имён нет в данных.
  Гибридный поиск чинит *способ* поиска, но не *отсутствие данных*.
- **A — компромисс:** имена 40.5% → 71.4%, но у сюжетных вопросов три фильма сдвинулись на
  одно место (Хатико 2→3, Астрал 3→4, Паразиты 7→8; все остались в top-8). Имена в конце
  документа оказались хуже по всем пунктам — интуиция «меньше мешают сюжету» не подтвердилась.
- **RRF работает с рангами, а не с оценками:** косинусное расстояние и `ts_rank` в разных
  шкалах, их нельзя сложить. k = 60 (из оригинальной статьи) не даёт первому месту одного
  списка задавить второй список.
- **`english`, а не `simple`:** документы английские — стемминг («robots» = «robot») и
  стоп-слова («how», «a» не считаются совпадением). Русские вопросы по тексту не совпадают
  ни с чем — их покрывает вектор.
- **Недетерминизм без tiebreak:** у многих документов одинаковый `ts_rank` (имя упомянуто
  один раз), и порядок шёл по физическому расположению строк — после переиндексации names
  MRR «прыгал» 0.738 ↔ 0.810. Первый замер 90.5% recall был **везением** порядка строк;
  честная цифра после tiebreak — 76.2%, и она не меняется даже после `VACUUM FULL`.
- **Разметка eval тоже может врать:** на «Keanu Reeves» 6 из 10 результатов — фильмы с
  Киану (оба «Джона Уика», «Матрица: Перезагрузка»…), а ожидается только «Матрица» (#10).
  Разметку не меняли задним числом, чтобы не подгонять ответ под результат.
- **Остался шум:** между фильмами с Киану вклиниваются «Гражданин Кейн» и «Джанго» —
  векторные попадания на 0.542, чуть ниже порога. «фильмы Кристофера Нолана» (кириллица)
  по тексту не совпадает, а по смыслу «Тёмный рыцарь» на 0.601 — порог его режет.
